# Brunova Language System v1

Status: Approved for implementation
Scope: Public website copy, metadata, accessibility text and text embedded in public visual assets
Languages: English and Spanish
Last reviewed: 2026-08-23

This document defines the language system for Brunova’s public website. It does not authorize page implementation by itself.

## 1. Voice

Brunova communicates as a systems engineering firm working close to complex operations.

The public voice is:

- concise;
- precise;
- executive;
- systems-engineering oriented;
- technically credible;
- calm and institutionally confident.

The public voice is not:

- generic marketing language;
- a software-agency portfolio voice;
- a consulting-services catalog;
- product-interface language;
- technical documentation presented without editorial hierarchy;
- anti-tool language.

Tools, software, automation and AI remain useful capabilities. The Brunova distinction is that they operate inside a designed system.

## 2. Conceptual hierarchy

```text
Operational intelligence / Inteligencia operativa
        ↓
Operating model / Modelo operativo
        ↓
Operational systems / Sistemas operacionales
        ↓
Operational capability / Capacidad operativa
```

### Level 1 — What Brunova builds

Approved:

- EN: Operational systems
- ES: Sistemas operacionales

Definition:

Systems that connect process, data, decisions, governance, software and automation around an operation.

Rejected or restricted:

- EN: Operating system, when referring to Brunova’s work.
- ES: Sistema operativo.
- ES: Sistema operativo empresarial.
- EN/ES: Solution / solución, when it replaces the more precise system concept.
- EN/ES: Product / producto, unless the subject is an actual product.

Usage examples:

- EN: Brunova combines engineering disciplines into operational systems.
- ES: Brunova integra disciplinas de ingeniería en sistemas operacionales.

### Level 2 — How Brunova designs systems

Approved:

- EN: Operating model
- ES: Modelo operativo

Definition:

The explicit structure of process, data, decisions, governance, boundaries and operating rules that determines how an operation should work.

Rejected or restricted:

- EN: Workflow, when the concept includes more than a sequence of tasks.
- ES: Flujo, when the concept includes the complete operating model.
- EN/ES: Process map / mapa de proceso, when the concept includes data, decisions and governance.

Usage examples:

- EN: The operating model defines how work, data and decisions connect.
- ES: El modelo operativo define cómo se conectan el trabajo, los datos y las decisiones.

### Level 3 — Result

Approved:

- EN: Operational capability
- ES: Capacidad operativa

Definition:

A reliable ability the organization can operate, govern and evolve in production.

Rejected or restricted:

- EN: Feature.
- ES: Funcionalidad, when the result is broader than a software function.
- EN/ES: Deliverable / entregable, when describing the resulting operational state.

Usage examples:

- EN: The operating model enables operational capability.
- ES: El modelo operativo habilita capacidad operativa.

### Level 4 — Differentiating approach

Approved:

- EN: Operational intelligence
- ES: Inteligencia operativa

Definition:

Brunova’s approach to connecting process, data, decisions, systems and governed execution in one operating model.

Rejected or restricted:

- EN/ES: Analytics / analítica, when the concept is broader than reporting or measurement.
- EN/ES: Business intelligence / inteligencia de negocio, when referring to the Brunova operating model.
- EN/ES: AI, when presented as the center of the system.

Usage examples:

- EN: Operational intelligence connects the operation to its operating model.
- ES: La inteligencia operativa conecta la operación con su modelo operativo.

## 3. Governance and ownership

### Approved system concept

- EN: Ownership
- ES: Gobernanza

In Brunova system language, this concept represents:

- authority;
- decision ownership;
- system evolution rules;
- operational control;
- accountability embedded in the operating model.

It does not represent:

- legal ownership;
- one person responsible for a task;
- task assignment;
- a job title.

Rejected for this system concept:

- ES: Propiedad.
- ES: Responsables.
- ES: Responsabilidad.

Usage examples:

- EN: Process · Data · Decisions · Ownership
- ES: Proceso · Datos · Decisiones · Gobernanza
- EN: The system boundary makes ownership explicit.
- ES: El límite del sistema hace explícita la gobernanza.

### Human responsibility exception

Use person-specific language only when the text genuinely refers to a person, role or task assignment.

Allowed examples:

- EN: The operating owner receives the handoff.
- ES: El equipo responsable recibe la transferencia.
- EN: The team identifies the current constraint.
- ES: El equipo identifica la restricción actual.

Do not mechanically replace every occurrence of `responsable` with `gobernanza`. Determine whether the sentence describes system authority or a person performing work.

## 4. Capabilities and engineering disciplines

Approved:

- EN: Capabilities
- ES: Capacidades
- EN: Engineering disciplines
- ES: Disciplinas de ingeniería

Usage distinction:

- Use `engineering disciplines / disciplinas de ingeniería` when describing what Brunova combines.
- Use `capabilities / capacidades` for navigation, taxonomy and the abilities involved in an operational system.
- Use `operational capability / capacidad operativa` for the resulting state enabled by the operating model.

Rejected or restricted:

- Services / servicios, when capabilities are presented as independent offers.
- Solutions / soluciones.
- Offerings / oferta de servicios.
- Service lines / líneas de servicio.

Usage examples:

- EN: Five engineering disciplines combine into one operational system.
- ES: Cinco disciplinas de ingeniería se integran en un sistema operacional.
- EN: Capabilities involved
- ES: Capacidades involucradas

## 5. Systems and tools

Approved position:

Isolated tools become insufficient when an operation requires a designed system.

Avoid:

- implying that tools are inherently bad;
- presenting architecture as an alternative to software;
- presenting automation or AI as the operating model itself.

Usage examples:

- EN: The problem is not the tool itself. The operation needs a system behind it.
- ES: El problema no es la herramienta en sí. La operación necesita un sistema detrás.

## 6. Automation, software and AI

Approved:

- EN: Automation / ES: Automatización
- EN: Software / ES: Software
- EN: AI / ES: IA
- EN: Governed capability / ES: Capacidad gobernada
- EN: Human review / ES: Revisión humana

Rules:

- Automation, software and AI operate inside the system boundary.
- AI assists where judgment can be bounded and governed.
- Human review remains explicit when operational judgment is required.
- Do not describe AI as the center of the system.

## 7. Process and engagement language

Approved stage verbs:

| EN       | ES           |
| -------- | ------------ |
| Discover | Diagnosticar |
| Design   | Diseñar      |
| Build    | Construir    |
| Evolve   | Evolucionar  |

Approved stage names:

| EN                     | ES                       |
| ---------------------- | ------------------------ |
| Systems Discovery      | Diagnóstico del sistema  |
| Architecture Blueprint | Diseño de arquitectura   |
| Implementation Sprint  | Sprint de implementación |
| Managed Evolution      | Evolución continua       |

Approved position:

- Engagement begins at the state that matches what is already known.
- Discovery is available when the problem is unclear; it is not mandatory.
- The public explanation prioritizes current situation, Brunova intervention and resulting state.

Rejected or restricted:

- Funnel / embudo.
- Sales process / proceso comercial.
- Mandatory sequence / secuencia obligatoria.
- Project-management language as the primary explanation.

Timelines may be used as supporting metadata, not as the main definition of a stage.

## 8. Work and system records

Approved:

- EN: Engineered systems
- ES: Sistemas diseñados y construidos
- EN: System record
- ES: Registro de sistema
- EN: Anonymized system record
- ES: Sistema anonimizado
- EN: Selected systems
- ES: Sistemas seleccionados

Rejected or restricted:

- Portfolio, when it makes Brunova read as a software agency.
- Project card / tarjeta de proyecto.
- Case showcase / escaparate de casos.
- Client story, when no client identity is published.

Usage examples:

- EN: Examples of operational systems engineered around different constraints.
- ES: Ejemplos de sistemas operacionales diseñados alrededor de restricciones distintas.

## 9. Data and integration language

Approved:

| EN                   | ES                        |
| -------------------- | ------------------------- |
| Data                 | Datos                     |
| Data engineering     | Ingeniería de datos       |
| Data pipeline        | Flujo de datos            |
| Extraction pipeline  | Flujo de extracción       |
| Reporting pipeline   | Flujo de reportes         |
| Data warehouse       | Almacén de datos          |
| Source system        | Sistema de origen         |
| Reference resolution | Resolución de referencias |

Restricted in public Spanish:

- Pipeline, when `flujo de datos`, `flujo de extracción` or `flujo de reportes` communicates the same meaning precisely.

Use `pipeline` only when it is required as a technical term and the audience benefits from the distinction.

## 12. Spanish editorial rules

Spanish copy must read as originally authored for CEOs, founders, COOs and operational leaders.

Use:

- direct sentences;
- explicit subjects when responsibility could be ambiguous;
- technical terms that are natural in an executive context;
- conceptual parity with English;
- `usted` consistently in direct contact language.

Avoid:

- literal English syntax;
- unnecessary gerunds;
- unexplained Anglicisms;
- documentation-style noun stacking;
- generic marketing phrases;
- translating `ownership` as `propiedad` in system contexts;
- translating `operational system` as `sistema operativo`.

## 13. English editorial rules

Use:

- active voice;
- short declarative sentences;
- precise system nouns;
- `engineered`, `designed` and `built` when they describe actual work;
- technical depth after the executive proposition is clear.

Avoid:

- agency portfolio language;
- broad consulting claims;
- repeated definitions of the same system concept;
- `operating system` when `operational system` is intended;
- `service line`, `solution` and `offering` as default category language.

## 14. Metadata and accessibility

- Metadata titles and descriptions use the same approved terminology as visible copy.
- SVG titles, descriptions and visible labels remain conceptually aligned.
- Mobile fallbacks use the same terminology as desktop assets.
- Accessible labels do not introduce deprecated terms.
- English and Spanish alternatives preserve meaning, not word order.

## 15. Review checklist

Before publishing public copy, verify:

1. Does the text distinguish operational intelligence, operating model, operational system and operational capability?
2. Does Spanish use `sistema operacional`, never `sistema operativo`, for the Brunova system concept?
3. Does the system concept use `Ownership / Gobernanza` consistently?
4. Are human responsibilities distinguished from system governance?
5. Are capabilities presented as connected engineering disciplines?
6. Are automation, software and AI inside the operating model rather than at its center?
7. Is the executive proposition clear before technical detail begins?
8. Are EN and ES conceptually equivalent?
9. Do metadata, accessibility text and visual assets use the same terms?
10. Does every factual statement remain supported by existing content?
